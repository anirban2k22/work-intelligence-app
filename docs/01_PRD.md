# PM Work Intelligence — Product Requirements Document (PRD)

- **Status:** Implementation-ready
- **Product:** PM Work Intelligence — AI Work Intelligence Platform
- **Document version:** 1.0
- **Applies to:** MVP scope

---

## 1. Executive Summary

PM Work Intelligence is an AI-powered work intelligence platform for Program Managers, Project Managers, Product Managers, Engineering Managers, and other knowledge workers. It is **not** a timesheet application.

The platform captures how users actually work through **natural conversation**, then uses AI to structure that input into accurate work logs, reports, analytics, and insights — aligned to the user's own configurable KRAs, projects, stakeholders, meetings, deliverables, and other work dimensions.

The product's core value loop is: **converse → structure → validate → report → decide**.

The MVP delivers a single-user, personal work intelligence experience: users converse with the AI about their work, review and correct the structured output, and consume daily/weekly summaries, basic analytics, and exportable reports. Everything that defines a user's work context (KRAs, projects, stakeholders, time-allocation categories) is editable and is used by the AI as interpretive context. The MVP ships as a web application with a React/Next.js frontend and a FastAPI backend.

## 2. Product Overview

### 2.1 What It Is

PM Work Intelligence is an AI work intelligence platform that:

- Lets users **record work through natural conversation** (typing or voice-dictated text).
- **Automatically structures** those conversations into work logs, including KRAs served, projects touched, stakeholders involved, meetings, deliverables, documentation, learning, bugs, features, and time allocation.
- **Generates reports and summaries** (daily, weekly, custom) in plain language.
- **Produces analytics and insights** — effort distribution, project progress, KRA contribution, stakeholder engagement, and pattern detection.
- **Uses user-configured context** (KRAs, projects, stakeholders, etc.) to interpret and categorize work accurately.

### 2.2 What It Is Not

- **Not a timesheet application.** No clock-in/clock-out, no hourly billing forms, no timesheet approvals.
- **Not a project management tool.** It does not manage tasks, tickets, sprints, or dependencies (though it understands and reports on projects).
- **Not a passive screen/activity tracker.** It captures intent through conversation and user-provided sources, not invasive activity monitoring.
- **Not a replacement for communication tools.** It ingests what users already communicate rather than replacing the channels.

### 2.3 High-Level User Flow

1. **Configure:** User sets up their work context (KRAs, projects, stakeholders, categories).
2. **Capture:** User talks to the AI about what they did (typed or pasted) at any cadence.
3. **Structure:** AI converts the description into structured work-log entries; flags low-confidence fields for confirmation.
4. **Validate:** User reviews, edits, confirms, or rejects entries. Corrections feed back to the AI.
5. **Report:** User generates daily/weekly/custom reports and summaries from validated records.
6. **Decide:** User (and their manager) act on analytics and insights generated from accumulated work records.

### 2.4 Core Entities

The MVP centers on these first-class, configurable entities:

| Entity | Description | Configurable? |
|--------|-------------|---------------|
| **KRA** | Key Result Area — a high-level responsibility area (e.g., "Platform Architecture", "Stakeholder Management"). | Yes — user creates, edits, archives, and orders KRAs. |
| **Project** | A named piece of work with goals, status, and dates. | Yes — user creates, edits, and archives projects. |
| **Stakeholder** | A person, group, or org unit the user works with. | Yes — user creates, edits, and archives stakeholders. |
| **Meeting** | A meeting the user attended or hosted, with purpose, attendees, and outcomes. | Yes — meeting types and outcome templates are editable. |
| **Deliverable** | A tangible output of work (doc, design, report, release, etc.). | Yes — deliverable types are editable. |
| **Documentation** | Docs, wiki pages, and notes produced/updated. | Yes — documentation types are editable. |
| **Learning** | Knowledge gained (courses, research, skill-building). | Yes — learning types/categories are editable. |
| **Bug** | Defect-related work. | Yes — bug attributes/statuses are editable. |
| **Feature** | Feature-related work. | Yes — feature attributes/statuses are editable. |
| **Work Log Entry** | The structured unit of recorded work, generated by AI from conversation. | Structure editable via configurable fields. |
| **Time Allocation** | Effort attributed to entries/categories over a period. | Yes — allocation categories and default rules are editable. |
| **Report** | Generated artifact (daily/weekly/custom summary, analytics export). | Yes — report templates are editable. |

## 3. Problem Statement

Knowledge workers — particularly PMs and engineering managers — are expected to produce accurate work records, status reports, and contribution evidence, but the mechanisms to do so are broken:

1. **Manual capture is abandoned.** Timesheets and status docs demand constant, tedious updates. They are abandoned within weeks and back-filled from memory, yielding inaccurate data.
2. **Raw activity capture misses intent.** Tool-level tracking captures apps and files, not *meaning* — which project, which KRA, which stakeholder.
3. **Context is hardcoded.** Existing tools cannot understand a user's specific KRAs, projects, or stakeholders. They categorize work into generic buckets that don't match how an organization actually operates.
4. **Reports are manual and late.** Status reports and retrospectives are written by hand, from memory, and are outdated before they are read.
5. **Decisions are evidence-light.** Performance reviews, resource planning, and prioritization happen on reconstructed narratives rather than reliable data.

The result: leaders make decisions on incomplete information, and individual contributors are misrepresented or undervalued because their work was never accurately recorded.

## 4. Goals

### 4.1 Product Goals

- **G1:** Enable users to record a complete, accurate day's work via a short natural-language conversation, with no form-filling.
- **G2:** Produce structured work logs aligned to the user's configurable KRAs, projects, stakeholders, and other entities.
- **G3:** Generate accurate daily/weekly reports, summaries, and analytics with minimal user effort.
- **G4:** Ensure every AI-generated claim has provenance (source conversation) and is human-verifiable.
- **G5:** Make every dimension of work context configurable and AI-aware.
- **G6:** Create a validation loop where user corrections improve AI accuracy.

### 4.2 Business Goals

- **G7:** Achieve activation (first confirmed AI-generated work log) within 48 hours of signup.
- **G8:** Reduce user time spent on work capture and reporting by ≥ 30%.
- **G9:** Retain weekly active users through daily-capture habit formation.
- **G10:** Establish the product as the trusted system of record for individual work intelligence, laying groundwork for team and organization expansion.

---

## 5. Non-Goals

- **N1:** No team/collaboration features in MVP (shared projects, org-wide reports, role-based multi-user access).
- **N2:** No timesheet compliance, approvals, or billing/invoicing features.
- **N3:** No project-management features (task boards, sprints, ticket systems, dependency management, Gantt).
- **N4:** No passive background monitoring, screenshots, or keystroke/activity capture.
- **N5:** No mobile apps in MVP (responsive web only).
- **N6:** No integrations with external tools (Slack, Jira, Outlook, calendar) in MVP — though the entity model anticipates them.
- **N7:** No multi-language support in MVP (English only).
- **N8:** No administrative role/permission management beyond single-user personalization.
- **N9:** No predictive/forecasting analytics in MVP (only descriptive analytics and rule-based insights).
- **N10:** No offline mode in MVP.

## 9. Functional Requirements

### FR-1: Authentication & User Profile
- **FR-1.1** User signs up with email and password; account is created with a default, empty configuration.
- **FR-1.2** User logs in/out; sessions persist securely.
- **FR-1.3** User can edit profile (name, role/title, display preferences).
- **FR-1.4** Password recovery (email link) is available.

### FR-2: Configurable Work Context
- **FR-2.1** User can create, edit, archive, and delete **KRAs** (name, description, priority, active status, ordering).
- **FR-2.2** User can create, edit, archive, and delete **Projects** (name, description, status, start/end dates, related KRAs, priority).
- **FR-2.3** User can create, edit, archive, and delete **Stakeholders** (name, role, organization, relationship type, contact/notes).
- **FR-2.4** User can create, edit, and delete **time-allocation categories** (labels and default color/order).
- **FR-2.5** All configured entities are editable at any time; edits propagate to AI interpretation behavior.
- **FR-2.6** User can archive (soft-disable) an entity without losing historical work-log references.

### FR-3: Conversational Work Capture
- **FR-3.1** User opens a capture session and describes work in free-form natural language (typed or dictation-to-text).
- **FR-3.2** The system supports multi-part descriptions (multiple activities, meetings, deliverables in one message).
- **FR-3.3** The system maintains conversation context within a session (follow-up messages can refer to earlier statements).
- **FR-3.4** User can paste meeting notes, chat snippets, or notes as a capture source.
- **FR-3.5** Capture history is stored and viewable per session.

### FR-4: AI Structuring & Extraction
- **FR-4.1** For each capture, the AI returns one or more candidate **work-log entries**.
- **FR-4.2** Each entry contains structured fields: summary, type (meeting/deliverable/documentation/learning/bug/feature/other), KRA(s), project(s), stakeholder(s), time allocation estimate, date(s), and free-form details.
- **FR-4.3** Extraction **must** use the user's configured KRAs, projects, stakeholders, and categories as the allowed/known values; unknown or ambiguous entities are flagged rather than invented.
- **FR-4.4** Each field carries a **confidence level**; low-confidence fields are surfaced for confirmation.
- **FR-4.5** When input is ambiguous (e.g., two matching projects), the AI asks a clarifying question instead of guessing.
- **FR-4.6** Every generated entry includes **provenance** (reference to the source text/session).
- **FR-4.7** AI never fabricates facts not present or reasonably inferable from the user's input; it labels inferences as such.
- **FR-4.8** The AI honors configured time-allocation rules when estimating effort.

### FR-5: Work Log Management
- **FR-5.1** User views work-log entries grouped by day/week, filterable by entity type, project, KRA, stakeholder, and status.
- **FR-5.2** User can confirm, edit, split, merge, delete, or reject any AI-generated entry.
- **FR-5.3** User can manually create entries (fallback) with the same fields.
- **FR-5.4** Entry status lifecycle: `draft` (AI-generated, unconfirmed) → `confirmed` → (optional) `archived`.
- **FR-5.5** Corrections made by the user are stored as feedback and associated with the relevant configuration context.

### FR-6: Reports
- **FR-6.1** User can generate a **daily summary** and **weekly summary** of confirmed work.
- **FR-6.2** User can generate a report over a **custom date range**.
- **FR-6.3** Reports are generated in plain-language narrative prose, grouped by KRA/project/type as configured.
- **FR-6.4** Reports are editable before export.
- **FR-6.5** Reports export to Markdown and PDF.
- **FR-6.6** Report templates are configurable (sections, tone, level of detail).

### FR-7: Analytics & Insights
- **FR-7.1** Dashboard shows effort distribution by KRA, project, and category over selectable time ranges.
- **FR-7.2** Time-allocation breakdown shows actual vs. planned allocation with configurable targets.
- **FR-7.3** Insights surface automatically: over-allocation to a KRA, weeks with no confirmed entries, projects without recent activity, high stakeholder engagement, and missing attribution.
- **FR-7.4** Insight rules are configurable (thresholds, enabled/disabled).
- **FR-7.5** Users can dismiss or acknowledge insights.

### FR-8: Learning & Feedback Loop
- **FR-8.1** User corrections to AI output are logged and associated with session context.
- **FR-8.2** Correction patterns improve future extraction (model refinement per user and/or per configuration).
- **FR-8.3** Users can provide explicit thumbs-up/down and textual feedback on AI structuring quality.
- **FR-8.4** AI quality reports are surfaced to product/ops for continuous improvement.

### FR-9: Settings & Data
- **FR-9.1** User can export all their data (work logs, configs, reports) in standard formats (JSON/CSV/Markdown).
- **FR-9.2** User can delete their account and all associated data.
- **FR-9.3** User can control AI behavior preferences (verbosity, clarification frequency, default attribution).

## 10. Non-Functional Requirements

### NFR-1: Performance
- **NFR-1.1** Conversational capture returns initial structured results in **< 10 seconds** for typical input (p95).
- **NFR-1.2** Dashboard and work-log views load in **< 2 seconds** (p95) on standard hardware.
- **NFR-1.3** Report generation completes in **< 15 seconds** (p95) for a month of data.

### NFR-2: Reliability & Availability
- **NFR-2.1** Core APIs target **99.9%** availability.
- **NFR-2.2** Work data is persisted durably; no data loss on capture-session interruption.
- **NFR-2.3** The system degrades gracefully when the AI provider is unavailable (structured manual entry remains fully functional).

### NFR-3: Security
- **NFR-3.1** All traffic over **TLS** in production.
- **NFR-3.2** Passwords hashed with a strong algorithm (e.g., bcrypt/argon2); never stored in plaintext.
- **NFR-3.3** OWASP Top-10 mitigations applied (auth, injection, XSS, CSRF, SSRF, rate limiting, secure sessions).
- **NFR-3.4** Row-level access control: users can only access their own data.
- **NFR-3.5** Secrets (API keys, DB credentials) managed via environment variables/secret manager; never in source control.

### NFR-4: Privacy & Data Governance
- **NFR-4.1** Users own their data; clear, plain-language privacy policy and consent.
- **NFR-4.2** AI provider requests minimize data (transmit only what is required for structuring); user data is **not** used to train shared models without explicit opt-in.
- **NFR-4.3** Full data export and account deletion are available and functional.
- **NFR-4.4** Data retention and deletion policies are documented and enforced.

### NFR-5: AI Quality
- **NFR-5.1** **≥ 95%** of user-confirmed entries require no field edits after generation, for routine descriptions (measured on confirmed entries).
- **NFR-5.2** Zero fabricated facts: system must never invent entities/claims not in or reasonably inferable from input (targeted test suite + monitoring).
- **NFR-5.3** Ambiguity detection: input with genuinely ambiguous entity matches is flagged for confirmation **≥ 90%** of the time.

### NFR-6: Usability
- **NFR-6.1** A new user completes configuration and generates a first confirmed work log within **15 minutes**.
- **NFR-6.2** Core tasks (capture, confirm, report) require **≤ 3 clicks** beyond the conversation itself.
- **NFR-6.3** Responsive design: fully usable on desktop and tablet; mobile browsers supported for capture.

### NFR-7: Maintainability & Extensibility
- **NFR-7.1** Modular architecture separating capture, structuring/AI, storage, and reporting.
- **NFR-7.2** Configuration-driven AI prompts: no hardcoded entity lists in code; all contextual vocabulary comes from configuration.
- **NFR-7.3** Comprehensive API documentation (OpenAPI).
- **NFR-7.4** Logging, tracing, and monitoring for all core flows.

### NFR-8: Compatibility
- **NFR-8.1** Supports current versions of Chrome, Firefox, Safari, and Edge.
- **NFR-8.2** API is versioned to allow backward-compatible evolution.

## 12. Acceptance Criteria

### AC-1: Signup & Login
- **AC-1.1** Given a valid email and password, when I submit the signup form, then an account is created, I am logged in, and I land on the onboarding/config screen.
- **AC-1.2** Given an invalid or duplicate email, when I submit signup, then I see a clear validation error and no account is created.

### AC-2: KRA Configuration
- **AC-2.1** Given the configuration screen, when I add a KRA with name and description, then it appears in the KRA list, is immediately used by the AI as a recognized KRA, and persists across sessions.
- **AC-2.2** Given an archived KRA, when I capture work mentioning it, then the AI does not auto-assign that KRA but may flag the mention for user resolution.

### AC-3: Natural-Language Capture → Structured Entries
- **AC-3.1** Given a capture message describing 3 distinct activities, when I submit it, then the AI returns 3 structured entries, each with a summary, type, entities, and confidence, and each referencing the source text.
- **AC-3.2** Given a capture that mentions "Project Phoenix" when the user has exactly one project named "Project Phoenix", then the AI attributes the entry to it with high confidence.
- **AC-3.3** Given a capture that mentions "the big one" when two projects could match, then the AI asks a clarifying question rather than guessing.
- **AC-3.4** Given a capture with no mention of any project, when the AI assigns a project, then the assignment is explicitly labeled as an inference.

### AC-4: No Fabrication
- **AC-4.1** Given a capture that mentions a stakeholder never configured and never named elsewhere, when the AI structures the entry, then it does not invent the stakeholder as a typed entity; it either leaves it as free text or flags it for creation.

### AC-5: Work Log Review
- **AC-5.1** Given a draft entry, when I click "Confirm", then its status changes to `confirmed` and it is included in reports and analytics.
- **AC-5.2** Given a draft entry, when I edit a field, then the correction is saved, reflected in reports, and recorded as feedback for model improvement.

### AC-6: Daily & Weekly Reports
- **AC-6.1** Given a user with confirmed entries in a date range, when I generate a weekly report, then the report contains narrative coverage of all confirmed entries, grouped by configured entities, and is exportable to PDF and Markdown.

### AC-7: Analytics Dashboard
- **AC-7.1** Given confirmed entries over the selected range, when I view the dashboard, then effort distribution charts by KRA, project, and category render with correct percentages summing to 100%.

### AC-8: Insights
- **AC-8.1** Given a week with zero confirmed entries, when I view the dashboard, then an insight "No work logged for this week" is surfaced and dismissible.

### AC-9: Data Export & Deletion
- **AC-9.1** Given a user with data, when I request a full export, then I receive a valid JSON/CSV/Markdown archive containing all work logs, configs, and reports.
- **AC-9.2** Given an account deletion request, when I confirm, then all personal data is deleted from primary storage within 30 days and I can no longer log in.

## 13. Success Metrics

### North Star Metric
- **NSM — Weekly Active Structured Work Sessions:** number of users who produce or validate at least one AI-generated work record in a given week.

### Acquisition & Activation
- **M1 — Activation rate:** % of signups who confirm their first AI-generated work log within 48 hours. **Target ≥ 40%.**
- **M2 — Time to first confirmed log:** **Target ≤ 15 minutes** from signup.

### Engagement
- **M3 — Weekly capture sessions per active user:** **Target ≥ 3/week.**
- **M4 — Daily active / weekly active (DAU/WAU) ratio:** **Target ≥ 0.5.**
- **M5 — Report generation rate:** % of WAU who generate ≥ 1 report/month. **Target ≥ 30%.**

### Quality & Trust
- **M6 — Confirmed-entry edit rate:** % of confirmed entries that required ≥ 1 field edit. **Target ≤ 5%.**
- **M7 — Clarification rate:** % of captures where the AI requested clarification. **Target 5–15%** (high enough to be careful, low enough to be frictionless).
- **M8 — Fabrication rate:** % of captured entries containing invented entities/claims (audited sample). **Target < 0.5%.**
- **M9 — Net Promoter Score (NPS):** **Target ≥ 50** at 6 months post-launch.

### Value & Business
- **M10 — Time saved:** self-reported + inferred hours saved on capture/reporting per active user per week. **Target ≥ 30% reduction.**
- **M11 — Weekly retention:** % of WAU retained week-over-week. **Target ≥ 80%.**
- **M12 — Paid conversion (post-trial):** **Target ≥ 15%** of trial users.

### Guardrail Metrics
- **G-M1 — P95 capture latency ≤ 10s.**
- **G-M2 — Availability ≥ 99.9%.**
- **G-M3 — AI-availability outage: manual entry must remain functional.**

## 14. Risks

| # | Risk | Impact | Likelihood | Mitigation |
|---|------|--------|-----------|------------|
| R1 | **AI hallucination / fabrication** — AI invents entities or claims, eroding trust. | High | Medium | Strict provenance on every claim; confidence labels; inference vs. stated labeling; clarification-on-ambiguity; eval harness with fabrication test suite; rate monitoring. |
| R2 | **Poor accuracy on ambiguous or niche vocabulary** — extraction quality low for unusual org terminology. | High | Medium | Configuration-driven context injected into prompts; correction feedback loop; per-user tuning; clarify-don't-guess behavior. |
| R3 | **Capture fatigue** — users abandon capture after novelty wears off. | High | Medium | Zero-burden default flow (paste + conversation); habit nudges; immediate value (reports) that justify capture; low friction at every step. |
| R4 | **Privacy concerns** — users worry the AI sees sensitive work data. | High | Medium | Plain-language privacy policy; explicit consent; minimize AI request payloads; no training on user data without opt-in; full export/delete. |
| R5 | **LLM API dependency & cost** — provider outage or rising costs. | Medium | High | Provider abstraction layer; graceful degradation to manual entry; request-size minimization; caching; multi-provider strategy; cost monitoring. |
| R6 | **Report quality below professional standard** — users must heavily edit generated reports. | Medium | Medium | Configurable templates; tone/verbosity settings; iterative prompt tuning with real corpus; edit-rate monitoring. |
| R7 | **Config burden on first run** — users churn during configuration. | Medium | Medium | Guided onboarding; sensible starter templates; "configure later" path that defaults to generic categories. |
| R8 | **Scope creep toward project-management/timesheet feature set.** | Medium | Medium | Explicit non-goals; product principles; disciplined roadmap; stakeholder alignment on positioning. |
| R9 | **Data lock-in concerns** — users worry they can't leave. | Medium | Medium | Open export (JSON/CSV/Markdown); documented data model; clear deletion path. |
| R10 | **Security breach / data exposure** | High | Low | OWASP mitigations; row-level access; secrets management; encryption in transit; security reviews and pen-testing before GA. |
